# サービスの提供状況

> 構成に AWS サービス名を書くとき、既存 doc のサービス言及を直すときに読む。
>
> English: [service-lifecycle_en.md](service-lifecycle_en.md)

読者はリファレンスに書かれたとおりに作ろうとする。新規顧客に開いていないサービスが
手順に出てくると、コンソールに作成経路がなく、その事実は文書のどこにも書かれていない。
失敗するのは読者側で、しかも読者が作業を始めてから分かる。

## 自動チェック

`scripts/check_sunset_services.py`（`make drift` 経由）。doc 単位で
「そのサービスに触れているなら、状況も同じ doc に書く」を強制する。

- 対象: `docs/**/*.md`, `usecases/**/*.md`, `cloud/**/*.md`, `edge/**/*.md`,
  ルートの `README*.md` / `TESTING*.md` / `CONTRIBUTING.md`
- 判定: サービス名を含み、状況を示す語句（`新規顧客` / `new customers` /
  `提供終了` / `discontinued` / `end of support` / `in maintenance` /
  `maintenance mode` / `sunset` / `非開放` / `サポート終了`）が同一 doc に無ければ落ちる
- 一覧は `SUNSET_SERVICES` に区分と出典 URL をコメントで併記して置く

行単位ではなく doc 単位なのは、同じサービスが本文と表で複数回出るため。行単位だと
注記のある 1 行以外がすべて落ちる。

> **注記の位置と代替の妥当性は機械では見られない。** ゲートが通ることは、
> 読者の目に入る位置に注記があることを意味しない。

## 書き方

区分が「新規顧客非開放」以降のサービスは、次のどちらかにする。

1. 言及を削除する
2. 状況を出典付きで注記し、新規構築向けの代替を併記する

代替は対称に書く。どの条件でどちらが適するかを示し、片方を劣ったものとして扱わない。

## 落とし穴

- **`maintenance` を単語として検査語に入れてはいけない。** このリポジトリは
  `predictive maintenance` を多用する。実測: 60 doc のうち 7 件がこの語を含み、
  検査語に入れた初版では、廃止サービスを注記なしで挙げた doc が「予知保全」の語で
  通過した。同一の欠陥 2 件のうち 1 件だけが報告された
- **改称は提供終了と違って静かに起きる。** 公式ドキュメントが書き換わるだけで
  what's new に出ないことがある。ゲートは改称を検出しない
- **一覧の外は検出されない。** ゲートが 0 違反でも、一覧に無いサービスが
  非開放になっていれば分からない。一覧は作成時点のスナップショット
- **`.md` 以外は見ていない。** テンプレートのコメントや docstring のサービス名は対象外

## 確認の手順

1. `aws.amazon.com/about-aws/whats-new/` の "service changes" / "service availability" 系
2. 各サービスの document history ページ（機能単位の非開放はここにしか出ないことがある）
3. 改称は公式ドキュメントの現行ページタイトルを見る
