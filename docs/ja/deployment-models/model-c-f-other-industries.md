# Model C〜F: 他業種での差分

> 最終確認: 2026-08-19

小売、医療、通信、エネルギーで、[Model A](model-a-single-factory.md) /
[Model B](model-b-multi-factory.md) と何が変わるかだけを扱います。

## この doc の性格

**このリポジトリには、これらの業種での実装も測定も業種固有の一次情報もありません。**
製造業のユースケースを対象に書かれた構成を、他業種に当てはめたときに
「どの判断が変わるか」を整理したものです。

各業種を A・B と同じ詳しさで書くことはしません。書ける材料がないまま
分量を揃えることになるためです。

> **規制・コンプライアンスについて法的判断を示しません。** どの規制が適用されるか、
> どの構成が要件を満たすかは、法務・コンプライアンス部門の領域です。
> ここでは「どの論点を持ち込む必要があるか」を挙げるに留めます。

## 4 軸での差分

A・B から変わるのは主に 4 つの軸です。業種ごとの詳細より、この軸で考えるほうが移植できます。

| 軸 | 何が変わるか |
|---|---|
| 規制要件 | 適用される規制、必要な記録、第三者監査の有無 |
| データ所在 | データが置ける場所、処理できる場所 |
| レイテンシ要求 | 判断が間に合う必要のある時間 |
| コスト構造 | 固定費と使用量の比率、拠点数の桁 |

---

## Model C: 小売エッジ

| 軸 | A・B との差分 |
|---|---|
| 規制要件 | 決済に関わる系統と、それ以外を分離する要求が入る。カメラ映像に来店者が写るため、映像の扱いに関する論点が増える |
| データ所在 | 店舗内で処理を完結させる要求が出やすい（映像を外に出さない） |
| レイテンシ要求 | 棚の欠品検知など、多くは分単位で足りる。決済連携は別系統 |
| コスト構造 | **拠点数が桁で違う。** 数百〜数千店舗になると、1 拠点あたりの固定費が支配的になる |

**設計上の帰結**: 拠点数が多い構成では、[Model B](model-b-multi-factory.md) の
「拠点ごとに固定費がかかる」構造が効きます。エッジ側のストレージを各店舗に置く前提が
成立しにくく、[Pattern 09](../aws-patterns/09-edge-agentic-ai.md) のように
デバイス上で完結させる比重が上がります。

**持ち込む論点**: 映像に人物が写る場合の扱い（[Pattern 06](../aws-patterns/06-video-analytics.md)
のセキュリティ節）。決済系統との分離。店舗ネットワークの帯域。

**未実装**: 小売のユースケースはこのリポジトリにありません。

---

## Model D: 医療エッジ

| 軸 | A・B との差分 |
|---|---|
| 規制要件 | 患者情報の扱いに関する規制が入る。記録の保持期間と監査要求が製造業より厳しくなる傾向 |
| データ所在 | 施設内・国内に留める要求が出やすい。生成 AI の呼び出し先リージョンが論点になる |
| レイテンシ要求 | 診断支援は即時性が求められる場合がある。バッチ分析とは別系統 |
| コスト構造 | 拠点数は中程度。監査とログ保持のコストが A・B より大きい |

**設計上の帰結**: データ所在の要求が強い場合、
[セキュリティ設計 §17](../security-design.md) の選択肢のうち、
エッジで処理を完結させる形かハイブリッド構成が候補になります。AWS が
[データ所在要件下での検索付き生成の構成例](https://aws.amazon.com/blogs/machine-learning/implement-rag-while-meeting-data-residency-requirements-using-aws-hybrid-and-edge-services/)
を公開しています。

**持ち込む論点**: 患者情報が含まれるかの判定。AI の出力を診断に使う場合の
人間による確認の位置づけ。監査ログの保持期間と改ざん防止。

**未実装**: 医療のユースケースはこのリポジトリにありません。
**規制への適合は評価していません。**

---

## Model E: 通信エッジ

| 軸 | A・B との差分 |
|---|---|
| 規制要件 | 通信の秘密に関する要求。設備の稼働に関する報告義務がある場合がある |
| データ所在 | 設備が地理的に分散する。国内でも複数地域にまたがる |
| レイテンシ要求 | **ここが最も違う。** 設備の異常検知にミリ秒〜秒が要求される場合がある |
| コスト構造 | 拠点数が多く、拠点ごとの設備が高価。テレメトリの量が桁で大きい |

**設計上の帰結**: レイテンシ要求が厳しいため、判断をクラウドに送る構成が成立しにくくなります。
[Pattern 09](../aws-patterns/09-edge-agentic-ai.md) の委譲の考え方が中心になり、
クラウド側は学習と横断分析に回ります。テレメトリ量が大きいため、
[Pattern 07](../aws-patterns/07-digital-twin.md) のカーディナリティの見積りが
そのまま設計を決めます。

**持ち込む論点**: 時系列データベースのカーディナリティ上限。設備テレメトリの
サンプリング間隔。エッジ側での集約（すべてを送らない）。

**未実装**: 通信設備のユースケースはこのリポジトリにありません。

## Model F: エネルギー・公益

| 軸 | A・B との差分 |
|---|---|
| 規制要件 | 重要インフラに関する要求。制御系（OT）への接続に関する規制が入る |
| データ所在 | 国内・特定圏内に留める要求が強い |
| レイテンシ要求 | 制御に関わる部分は即時。監視・分析は分単位で足りる |
| コスト構造 | 拠点数は少〜中。設備の寿命が長く、既存機器との接続が中心になる |

**設計上の帰結**: **制御系との境界が最重要になります。**
[セキュリティ設計 §13](../security-design.md) の OT/IT 境界の原則
（データフローを一方向に保つ、障害の影響を OT 側に広げない）が、
このモデルでは要求として扱われます。既存機器が多いため、
[Pattern 08](../aws-patterns/08-unified-namespace.md) の名前空間設計から
入る価値が高くなります。

**持ち込む論点**: 制御系への書き戻しを設計に入れるかどうか（入れないのが既定）。
OT プロトコルからの収集点をどのセグメントに置くか。データ所在要件。

**未実装**: エネルギー・公益のユースケースはこのリポジトリにありません。
**重要インフラ向けの規制への適合は評価していません。**

---

## まとめ: どの軸が効くか

| モデル | 最も効く軸 | 参照すべきパターン |
|---|---|---|
| C 小売 | コスト構造（拠点数の桁） | [09](../aws-patterns/09-edge-agentic-ai.md), [06](../aws-patterns/06-video-analytics.md) |
| D 医療 | データ所在 | [05](../aws-patterns/05-agentic-rag.md), [09](../aws-patterns/09-edge-agentic-ai.md) |
| E 通信 | レイテンシ要求 | [07](../aws-patterns/07-digital-twin.md), [09](../aws-patterns/09-edge-agentic-ai.md) |
| F エネルギー | 規制要件（OT 境界） | [08](../aws-patterns/08-unified-namespace.md), [03](../aws-patterns/03-industrial-iot-analytics.md) |

**4 業種すべてで [Pattern 09](../aws-patterns/09-edge-agentic-ai.md) が出てきます。**
理由は共通で、「データを外に出せない」「レイテンシが足りない」「拠点数が多くて
クラウド往復のコストが合わない」のいずれかが、製造業より強く出るためです。
