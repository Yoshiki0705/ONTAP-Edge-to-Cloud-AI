# ビジネスストーリー: Edge-to-Cloud AI

> 「既存のエンタープライズデータを、IoTとAIで業務価値に変える」

---

## なぜ今か（タイミングの必然性）

以下の3つの技術的条件が 2024-2025 年に揃ったことで、このアーキテクチャが初めて実現可能になった:

| 時期 | 出来事 | 本プロジェクトへの影響 |
|------|--------|---------------------|
| 2024年7月 | SORACOM Flux GA | カメラ画像 × 生成AI の低コードパイプラインが可能に |
| 2025年2月 | FSx for ONTAP S3 Access Points GA | 既存NASデータをコピーなしでAI/分析に接続 |
| 2024-2025年 | Claude Vision / マルチモーダルAI の成熟 | 汎用プロンプトで産業用画像判定が実用精度に到達 |

**1年前にはできなかったこと:**
- Flux がなければ、カメラ→AI のパイプラインに数週間の開発が必要だった
- S3 AP がなければ、ONTAP データを S3 にコピーする ETL が必要だった
- Vision AI が未成熟なら、カスタムモデル学習に数ヶ月と大量の教師データが必要だった

**今だからこそ**: 1-2週間で PoC が動き、既存データ資産を活かし、プロンプト変更だけで新しい検査対象に適用できる。

---

## エレベーターピッチ（30秒）

> 工場や拠点のONTAP NASには、検査画像・設備ログ・センサーCSVが日々蓄積されています。
> しかし、そのデータの多くは「保存されているだけ」で活用されていません。
>
> 本アーキテクチャは、Raspberry Pi + SORACOM のエッジデバイスで現場データを収集し、
> AWS の AI/分析サービス（Bedrock、SageMaker、Athena）に直接つなぎます。
> ONTAP の SnapMirror と S3 Access Points により、データコピーなしでAI分析が可能です。
>
> 結果: 検査工程の自動化、設備故障の予測、運用コストの削減。

## なぜ3Dプリンター監視がデモなのか

3Dプリンター監視は **入口** であり、本当の価値ではない。

| 観点 | 3Dプリンター監視 (デモ) | 本当の価値 (汎用パターン) |
|------|------------------------|--------------------------|
| 対象 | 1台のプリンター | 工場全体の設備・検査工程 |
| データ | カメラ画像 | 画像 + センサー + ログ + ファイル |
| AI | 欠陥検出 | 予知保全 + 品質予測 + レポート生成 |
| ストレージ | S3 のみ | ONTAP (既存NAS) + FSxN + S3 |
| スケール | 1デバイス | 数十〜数百デバイス |
| 顧客 | Maker/個人 | 製造業/物流/ビル管理 |

**3Dプリンター監視を選んだ理由:**
1. 視覚的にわかりやすい（デモ映えする）
2. 最小構成で動く（Pi + カメラ + プリンター）
3. 失敗が頻繁に起きる（テストデータが自然に集まる）
4. 全パターンの縮図（画像AI + イベント駆動 + データ蓄積）

## ターゲット顧客と課題

### 顧客セグメント

| セグメント | 課題 | 本アーキテクチャの価値 |
|-----------|------|----------------------|
| **製造業 (ONTAP既存顧客)** | NAS上の検査画像が活用されていない | SnapMirror + S3 AP でデータ移動なしにAI分析 |
| **物流・倉庫** | 目視検査に人手がかかる | カメラ + Bedrock で自動化 |
| **ビル管理** | 設備故障が事後対応 | センサー + SageMaker で予知保全 |
| **農業** | 圃場の状態把握が手動 | 定点カメラ + AI で自動モニタリング |

### ONTAP 既存顧客への訴求ポイント

> 「今あるONTAPのデータを、コピーせずにAIで活用できます」

1. **データ移動不要**: S3 Access Points で既存NFS/SMBデータに直接S3 APIアクセス
2. **既存運用を変えない**: 現場のワークフロー（NFS書き込み）はそのまま
3. **段階的導入**: まずテレメトリ収集から始め、画像AI、予知保全へ拡張
4. **データ保護**: SnapMirror + ARP/AI で安全にクラウド連携

## アーキテクチャパターンの比較

本プロジェクトのアプローチと、他のアプローチの特徴を整理します（どれが「正解」ということではなく、要件に応じて選択）:

| 観点 | ONTAP 中心 (本プロジェクト) | S3 直接アップロード | IoT プラットフォーム利用 |
|------|--------------------------|-------------------|----------------------|
| 既存NASデータ | そのまま活用可能 | S3にコピーが必要 | プラットフォーム依存 |
| エッジ接続 | NFS/SMB (LAN) | HTTPS/MQTT | プラットフォーム SDK |
| 適するケース | 既存NASにデータ蓄積がある | 新規構築、データがまだない | マネージド運用を重視 |
| 制約 | ONTAP が必要 | ファイルワークフローとの統合が別途必要 | ベンダーロックインの可能性 |

> **注**: 本プロジェクトは「既存 ONTAP にデータがある」前提で設計しています。新規にストレージを導入する場合は、S3 直接アップロードの方がシンプルな場合があります。

## ビジネス成功指標（技術指標ではなく）

| 指標 | 測定方法 | PoC 目標 | 本番目標 |
|------|---------|---------|---------|
| 検査工数削減率 | (現状工数 - 導入後工数) / 現状工数 | 削減可能性の確認 | 50% 削減 |
| 不良品早期検出率 | AI検出 / 全不良品 | ≥ 70% | ≥ 90% |
| 無人運転可能時間 | 人手介入なしの連続運転時間 | 8時間/日 | 24時間/日 |
| フィラメント/材料浪費削減 | 失敗検知による早期停止で節約した材料費 | 測定開始 | 30% 削減 |
| 計画外停止回数 | 月間の予期しない設備停止 | ベースライン測定 | 50% 削減 |

> **重要**: 技術指標（精度80%、レイテンシ60秒）は手段。ビジネス指標が本当の成功基準。

## AI 判断の位置づけ（ガバナンス）

| 項目 | 定義 |
|------|------|
| **AI出力の性質** | 参考情報（assistive signal）。最終判断ではない |
| **自動アクション** | severity: high/critical の場合のみ自動停止。それ以外は人間が判断 |
| **責任範囲** | AI は「疑わしい」と通知する。停止/続行の最終判断はオペレーター |
| **誤検知時の影響** | 印刷一時停止（再開可能）。不可逆な損害は発生しない設計 |
| **見逃し時の影響** | フィラメント浪費、印刷時間のロス。安全上の危険はない |

### 安全な実験の境界

| やって良いこと | やってはいけないこと |
|--------------|-------------------|
| AI アラートを無視して印刷を続行 | AI 判断のみで高額材料の廃棄判断 |
| 閾値を変更して精度を調整 | 安全装置（温度リミッター等）を AI で無効化 |
| 新しいプロンプトを試す | 顧客の本番環境で未検証のプロンプトを使用 |
| 撮影間隔を変更する | 個人が映り込む場所にカメラを設置 |

## ROI 試算（製造業の例）

### 前提条件

- 検査工程: 1ライン、目視検査員1名 (年収500万円)
- 検査頻度: 1分に1回、8時間/日、250日/年
- 不良率: 2%、不良品1個あたりの損失: ¥5,000

### コスト比較

| 項目 | 現状 (目視検査) | 本アーキテクチャ導入後 |
|------|---------------|---------------------|
| 人件費 | ¥5,000,000/年 | ¥2,500,000/年 (50%削減: 検査員→監視員) |
| 不良品損失 | ¥6,000,000/年 | ¥3,000,000/年 (50%削減: 早期検出) |
| システム費用 | ¥0 | ¥600,000/年 (AWS + SORACOM + ハードウェア) |
| **合計** | **¥11,000,000/年** | **¥6,100,000/年** |
| **削減額** | — | **¥4,900,000/年** |

> **注意**: 上記は仮定に基づく概算。実際のROIは現場の状況により大きく異なる。導入前に現場アセスメントが必要。

## 提案の進め方

```
Step 1: デモ (1日)
  3Dプリンター監視のライブデモを見せる
  → 「こういうことが、御社の検査工程でもできます」

Step 2: アセスメント (1-2週間)
  現場訪問: データソース、ネットワーク、既存ONTAP環境の確認
  → PoC スコープの合意

Step 3: PoC (4週間)
  御社の実データ・実環境で小規模検証
  → Go/No-Go 判定

Step 4: パイロット (2-3ヶ月)
  1ライン/1拠点で本番運用
  → 効果測定、横展開計画

Step 5: 本番展開
  全ライン/全拠点に展開
  → 継続的改善
```
