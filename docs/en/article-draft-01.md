## TL;DR

Data generated by IoT devices in factories and sites tends to be scattered per-device and per-site. This article shares the design of a hybrid pipeline that aggregates data into ONTAP, performs real-time analytics with Kafka + ClickHouse, and runs image AI inference with AWS Bedrock. The first validation target is "3D print quality monitoring."

## 1. The Problem

When visiting sites, I often see situations like:

- Camera images in the printer's built-in cloud
- Sensor data on a Raspberry Pi's SD card
- Equipment logs scattered on a Windows PC

Data is being generated, but there's **no way to analyze it across sources**. On top of that, on-premises environments often lack analytics infrastructure and governance tooling, making "you have to build the tools first" the barrier to getting started.

## 2. Approach: Aggregate → Real-Time Analytics → AI

A three-layer hybrid architecture:

```
[Edge]            [Data Hub]          [Real-Time]        [AI/Analytics]
Raspberry Pi  →   ONTAP (NFS)     →   Kafka           →  AWS Bedrock
Camera/Sensor     Image/CSV store      ClickHouse         Athena/Glue
              →   Kafka (event)        Dashboard          Databricks
```

**The key design choice is "separating payload from event."**

- **Payload** (large: images, CSV): Edge → NFS → ONTAP
- **Event** (metadata: when, where, what): Edge → Kafka → ClickHouse

By keeping large binaries in ONTAP and flowing only lightweight metadata through Kafka, real-time analytics stays fast while original data accumulates locally.

## 3. Why This Architecture

### Why ONTAP as the data hub
- Serves NFS / SMB / S3 on the same data (multi-protocol)
- Leverages existing NAS workflows as-is
- Direct AWS access via S3 Access Points (no data copy)

That said, **the core pattern works without ONTAP**. S3-direct or EFS can achieve it too — compared later in this article.

### Why Kafka + ClickHouse on-premises
- Low latency by placing them on the same LAN as the edge (Pi)
- ClickHouse is a fast real-time analytics engine (columnar)
- Analytics continues locally even if the factory network disconnects from the cloud

### Why AI in the cloud (Bedrock)
- No local GPU needed, pay-per-use
- Claude Vision reaches practical accuracy for industrial image judgment with prompts alone (no custom model training)

## 4. What I Learned (Validation Stage)

### 85% cost reduction with two-stage AI analysis
Analyzing every image with a high-accuracy model (Claude Sonnet) costs ~$259/month. Screening with Haiku and escalating only suspected anomalies to Sonnet drops it to ~$40/month. This pattern applies to other AI pipelines too.

### Design disconnection resilience around "local is truth"
Factory networks are unstable. So:
- ONTAP saves don't depend on Kafka state (NFS is local LAN)
- On Kafka outage, buffer JSON locally → replay in chronological order on recovery
- Idempotence via event_id eliminates duplicates on replay

### The value of unifying the schema first
I defined a unified event envelope (event_id, site_id, equipment_id, payload_uri, ...) up front for events flowing Edge → Kafka → ClickHouse → Databricks. This makes four different systems consistent at the type level, avoiding rework later.

## 5. Storage Options Comparison

ONTAP is assumed, but the problem (aggregate → analyze) is solvable elsewhere.

| Storage | Strengths | Constraints |
|---------|-----------|-------------|
| S3 direct | Simplest, AWS native | No NFS/SMB |
| EFS | NFS mountable, Linux-friendly | No SMB, no direct S3 API |
| ONTAP | NFS+SMB+S3 same data, FPolicy, SnapMirror, ARP/AI | Requires ONTAP |

**How to choose**: S3 for greenfield, EFS for NFS writes, ONTAP if you have existing NAS and need both NFS+SMB.

## 6. Current Limitations

- **Hardware testing in progress**: Cloud side (Lambda, Bedrock) verified. Pi → ONTAP E2E is next

- **Single-device setup**: Scale-out not yet validated
